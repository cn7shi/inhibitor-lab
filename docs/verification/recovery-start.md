# R3：确认后的单次启动与实际关联

日期：2026-10-05。基线 `e68ea4c`；本阶段实现 `recovery start --plan <plan.json>`。准备和确认沿用 R2，实际执行共用原启动器。没有安装工具或新增依赖。

## 实现及结果解释

启动严格检查确认结构、父资格、计划位置和全部来源摘要，再唯一创建并同步 `.start.json`，占位后再次复核。执行内存中的规则快照和新配置，重新创建规则引擎、Pi 适配器与准入门禁。子进程使用确认的工作目录与预留运行 ID。

首条 `run_started` 保留 PID，第二条 `run_linked` 绑定父运行 / 摘要、计划与确认摘要；父日志不改。`inspect` 验证关联位置、字段、子身份并显示 `linkage`，不会为诊断递归执行或认证外部文件。正常再次关闭的子日志可以成为下一份明确准备的计划的父日志。

启动结果单独保存 `.result.json`，绑定启动占位摘要。`run_finished` 表示记录到完整终态，控制失败仍返回 2；不能将这个状态解释为恢复成功。`spawn_failed` 表示创建失败，`runner_failed` 表示创建后执行器异常，`not_spawned` 表示占位后的检查 / 初始化阶段失败。只有 `launcher_exit_code: 0` 和 `control_outcome: completed` 表示本次协议正常完成，不评价模型任务质量。再次关闭正常收尾返回 3。

`.confirmed.json` 的 `confirmed_not_started` 保留确认时的历史事实，不是实时状态。占位一旦存在，包括半文件，同一计划不再启动；没有完整结果可能是仍在运行或结果未知。创建进程和写入文件不是事务，不能自动重试或声称恰好一次执行。

## 可重复进程回归

`cargo test --locked` 覆盖总计 **62 项**：7 项库测试、8 项采集、16 项控制、12 项诊断、19 项恢复。恢复部分保留 R2 的 11 项，新增下列 8 项，使用实际 Rust 进程与 `mock-agent`，不是仅测试 JSON 函数。

| 场景 | 已观察结果 |
| --- | --- |
| 正常启动、关联、计数重置和再次关闭 | 子 ID 等于预留 ID；前两次请求获准，第二个失败才触发，第三次拒绝；退出 3；子日志再次准备成功 |
| 正常完成、工作目录、重复消费 | 标记只在所选目录产生一次；退出 0；重试返回 2，计划、确认、父日志、启动、子日志及结果字节不变 |
| 两启动进程竞争 | 退出码分别 0 / 2；实际子进程启动标记只有一行 |
| 未确认、取消或内容变化 | 缺确认、取消、父 / 配置 / 规则 / 计划变化、确认摘要错误、未知字段和半确认均拒绝；没有占位或子日志 |
| 已有启动、子日志或结果 | 包括半文件，均不覆盖、不创建进程；启动占位存在时诊断明确指出结果可能未知 |
| 创建失败与控制失败 | 非可执行文件导致 `spawn_failed`；缺门禁导致 `run_finished + failed`；均返回 2，重复启动拒绝 |
| 关联记录损坏 | 错 ID、坏摘要、自指父 ID、未知字段、缺失或后移关联均诊断拒绝 |
| 创建后输出管道中断 | 关闭实际管道读端，转发失败记录 `runner_failed`、已有 PID、无完整终态；返回 2，禁止重试 |
