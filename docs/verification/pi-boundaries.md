# Pi 并发与嵌套准入边界

日期：2026-10-05。基线：`ef64b8f`。本报告补充[上一阶段准入实验](pi-gate.md)，记录本地实测；[Check 工作流](https://github.com/cn7shi/inhibitor-lab/actions) 对本阶段提交执行相同验证。

## 结论

关闭准入可以阻止后续新请求，包括通过标准接口发起的两层嵌套请求与拒绝后的再次尝试；它不会撤销同一批已经批准的工具。四组真实 Pi 对照均验证了预期行为，本阶段无需修改生产准入逻辑。

这是合作式准入的边界验证，不是任意插件或操作系统副作用隔离。真实模型、任意深度、嵌套内部并行和人工恢复尚未验证。

## 实验方法

沿用 Windows、Scoop Node 24.20.0 / Rust 1.96.0、固定 Pi 1.0.3。模型服务只监听本机临时端口，固定返回工具调用，不需要密钥或付费服务。每组独立配置与工作目录，文件不存在时才开始；没有增加固定睡眠或竞态缓冲等待。

**批次实验**：第一条模型回复包含 `read missing-a.txt`、`read missing-b.txt`、`write batch-admitted.txt` 三个工具。第二条回复同时请求写入 `batch-later.txt`、`batch-retry.txt`。脚本断言第一批三次批准都早于任何工具结果，后续写入逐个关联新的准入决定。

**嵌套实验**：模型只请求 `lab_nested`，它通过 `ctx.executeTool()` 调用 `lab_sequence`，后者依次调用两次内置 `read` 和两次内置 `write`。即使首次写入被拒绝，也再请求一次写入。测试扩展只组织调用、收集结果，不直接写文件。父工具正常返回表示“收集完成”，不代表其子工具全部成功；测试明确核对两次读取失败。

每次批准对应扩展应用确认，每次拒绝关联同一次规则触发；文件必须包含精确测试内容或明确报 ENOENT。所有组均核对实际 Pi 退出码为 0、采集 / 适配完整以及没有强制清理。

### 具体证据

- 批次 record：`runs/pi-boundary-batch-record-FCi8fz/`，批准序号 30、36、42、72、79，触发序号 50。
- 批次 block：`runs/pi-boundary-batch-block-QPSJTl/`，前三个批准序号 30、36、42；失败结果原文 46、48；触发 50，关闭 51；同批写入成功结果原文 52。后续拒绝决定 73、82，合成结果原文 77、86，最终确认拒绝 2 个。
- 嵌套 record：`runs/pi-boundary-nested-record-MZLn20/`，六次批准序号 24、30、36、44、54、63，两个文件存在。
- 嵌套 block：`runs/pi-boundary-nested-block-q5Y2LK/`，父工具及两次读取准入 24、30、36、44，触发 50，写入拒绝 55、64，两个文件不存在。

批次写入的批准发生在触发之前，其成功结果在关闭之后被采集到；这不证明文件写入的系统调用恰好发生在关闭之后。可证实的是同批批准没有被撤销，后续新批准受到限制。采集序号不能替代工具内部执行时间。

嵌套 block 中，`nested_root/1` 回指父工具 `nested_root`；四个子调用 `nested_root/1/1` 至 `/4` 都回指 `nested_root/1`。原始结束事件序号分别为 40、48、59、68，子工具本身结束为 70。脚本核对这五条父子关系和各自准入，摘要保留 `parent_links`。原始协议仍保存在 `output`，未为展示而修改生产事件格式。

## 决策与剩余范围

继续使用“停止批准新请求”的契约；不把门禁关闭描述为停止整个父工具或撤销所有已批准调用，详见 D011。Pi 默认批次会先完成准入再执行，不能简单在准入钩子内等待上一工具结束，否则可能阻塞整批。

人工恢复应基于明确的触发依据和关闭状态另行设计。若要更严格限制同批提前放行，需要独立的调度契约，并验证嵌套与并行组合。插件自行执行文件操作或派生进程不受本协议保证；嵌套父工具再次报告失败仍按独立调用计数，本轮不做根因去重。
