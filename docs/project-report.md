# inhibitor-lab 项目总报告

截至 2026-10-05，覆盖阶段 0–10。本轮起点 `c93f324`；新协作者的源码入口仍是 [tutorial.md](../tutorial.md)，操作入口是 [README](../README.md)。本报告按证据复盘工作，不替代阶段原始记录。

**当前结论：已经完成“采集 → 规则触发 → 控制 → 核验证据 → 明确确认 → 关联新运行 → 查看状态”的本地原型闭环。** 真实 Pi 与真实文件操作参与验证，模型由固定测试服务代替。尚未进入真实模型联调、试点或生产使用阶段。

## 1. 问题背景

用户希望治理 Agent 在本地工作时反复出错的过程：能取得信息、按规则触发、限制继续执行，并让人理解原因后决定如何继续。此前要求使用者转到专用页面的方向增加了接入负担，因此用户提出管道启动器配合本地日志和 MCP 观测。

双方把首轮目标收窄为可靠取信息和显式规则触发，暂缓智能判错。随后按用户选择，用轻量、开源的 Pi 作为第一个接入对象；另建私有 `inhibitor-lab`，从头实现，借鉴旧 Inhibitor 的意图。实际完成的是管道和 Pi 接入；日志文件跟随、MCP 仍属于设想。

治理范围是“本次运行累计两次工具明确报告失败”一类条件。正文含 ERROR、stderr 有输出、模型声称失败，都不能直接替代工具结果；也没有推断相同根因或连续失败。

## 2. 方案决策

| 决策 | 理由与代价 | 可追溯依据 |
| --- | --- | --- |
| 先显式规则，再智能判断 | 先证明输入与触发可重复；暂不判断语义正确性 | D001–D003 |
| Rust 核心 + Pi 适配和扩展 | 规则依赖统一事件，Pi 协议隔离在接入层；控制仍需 Agent 合作 | D002、D010 |
| 固定模型服务先行 | 不依赖账号、错误序列可复现；不能代替真实模型表现 | D003、D016 |
| 分开 RPC 中止和执行前准入 | 收到失败后的中止有时间窗口；工具执行前等待许可才能限制新请求 | D008、D010–D011 |
| 恢复创建关联新运行 | 用户明确选择“查看原因、确认、开启新运行”；独立计数和日志更容易核验 | D012–D016 |
| 计划、确认、启动占位、结果分开 | 内容变化使旧许可失效，唯一占位避免同计划竞争启动；文件和进程仍无事务保证 | D014–D015 |
| 状态报告只读，历史与当前来源分开 | 已发生事实不因配置后来删除而消失；缺结果不能推断没执行或成功 | D017 |

完整理由、备选和适用条件见 [决策记录](decisions.md)。最重要的控制边界来自真实对照：Pi 的同一批工具可能提前全部获准，关闭只能拒绝后来的新请求。当前没有撤销已有许可的调度器。

## 3. 个人动作：谁决定、谁实施

用户负责确定产品问题与范围：不强制进入指定页面、独立新工程、先简单规则、采用 Pi、暂缓模型配置、开发环境优先 Scoop，以及人工恢复采用关联新运行。用户还明确要求阶段、编码与决策留档，并提出用阿里 OpenCodeReview 自查。

当前编程助手依据这些选择完成 Rust / Pi 实现、测试与故障复现、修复、依赖和环境核查、文档、Git 提交以及 CI 核对。具体实现与结果可通过 [开发记录](development-log.md)、源码、测试及提交逐项核验；不能写成用户逐行编写或独立完成了全部代码。

Pi 提供真实 CLI 与工具执行；Scoop 管理约定的开发工具，项目 npm 锁定 Pi 依赖。OCR 委托模式提供文件筛选和审查规则，判断、复现与修复由当前助手负责。没有第二个独立审查模型，未配置 OCR 自有模型 API。本轮没有新增工具或依赖。

## 5. 落地范围

已验证环境为 Windows、Rust 1.96.0、Node 24.20.0、Pi 1.0.3。开发工具优先由 Scoop 管理；项目内 npm 依赖与 MSVC / Windows SDK 的既有例外记录见教程和阶段记录。本轮没有脱离 Scoop 新装工具。

当前有三组入口：`run` 启动并治理；`inspect` 只读诊断单次日志；`recovery prepare/confirm/start/status` 管理经人确认的新任务。事件有运行 ID、连续序号、原始输出和控制引用。父日志保持原文，新运行的第二条事件保存关联。

R5 汇总待确认、待启动、来源失效、完成、再次关闭、失败、未知、证据无效。报告只读，历史结果与当前来源分开；“明确失败”的状态命令也可返回 0，调用方必须读取状态字段。缺结果或读取期间记录变化保守显示未知，不查询 PID 存活来猜测结果。

## 7. 个人边界与系统边界

当前助手的结论基于本地代码、日志、回归和 CI；用户的产品判断、助手实现、Pi 的运行行为、Node 运行时变化分别记录，不能互相替代。例如早期中止后崩溃在 Scoop 升级 Node 后消失，支持环境相关判断，但没有独立调试原生崩溃栈来证明全部根因。

以下能力不在已交付保证内：

- 真实模型语义判断、根因分析、自动修复、自动重试、原会话继续及完整上下文恢复。
- 本地日志文件跟随、MCP 观测、跨来源重复事件治理及通用 Agent 接入。
- 撤销已经批准的工具、任意后代进程树终止、系统级隔离或硬实时期限。
- 对同权限整套改写的防伪认证；摘要只检查一致性，未绑定二进制、脚本、环境和整个工作目录。
- 进程与文件创建的原子事务、断电 / 磁盘耗尽下恰好一次执行、长期负载稳定性。

“结果未知”是明确保留的状态。占位存在就不能直接重用该计划；已知失败也不等于所有后代及副作用都消失。控制是否发生、实际影响是什么、任务质量是否合格，是分别需要证据的问题。

## 附：升维迁移

可确认的普通事实：第二次工具失败后关闭新准入，用户确认后开启关联的新运行。

更有解释力的表达：围绕“事实—规则—控制—确认—结果”保留可核对的关联，让再次失败和结果未知都具有明确处理边界，而不是仅展示一条错误提示。

这里把单次功能动作提升为治理机制与证据链，收益目前仍是可追溯、可复现的技术能力；没有把它扩大成未经证明的业务收益。
