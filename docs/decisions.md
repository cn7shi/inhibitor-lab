# 决策记录

## D017：状态报告核对历史链，当前来源单独说明（2026-10-05）

- 接口 `recovery status --plan <path> [--format text|json]` 只读取，以计划规范位置派生四个配套文件路径，不按记录中任意路径跳转读取子日志或结果。状态为 `awaiting_confirmation`、`awaiting_start`、`stale_inputs`、`completed`、`blocked`、`failed`、`outcome_unknown`、`invalid_evidence`；固定 `authorizes_start: false`。
- 计划结构 / 位置 / 身份、确认摘要、启动占位和结果严格核对；完整终态还需复用日志诊断，比较实际子 ID、PID、关联、控制结果与返回码。结果缺失 / 未写完只能报告未知，即使子日志看似完成也不替代缺失结果；矛盾证据报无效。失败记录按未创建、创建失败、运行器失败或完整失败收尾分别解释。
- 当前父日志、配置、规则和路径另外检查，标为匹配或变化 / 不可读。启动前变化报告 `stale_inputs`；历史关联链完整时，已完成 / 再次关闭 / 失败结论保留，当前来源变化独立提示，不篡改历史。摘要不认证作者，当前匹配也不保证程序、环境或测试服务可用。
- 五份恢复记录先有界读取，再读取比较一次；观察到变化则结果未知，用户重新查看。计划最多 2 MiB，确认 / 占位 / 结果各 64 KiB，子日志 32 MiB；不是全目录原子快照或文件锁，不抵御同权限改写。半占位保守保留，不删除、不重试、不探测 PID 存活以推测结果。
- 退出 0 仅表示可确定的报告，包括明确失败；未知、来源失效或无效证据退出 2。未知 / 失败时提示人工核对进程和效果；状态命令从不触发模型、写日志或开启下一次运行。R1–R4 运行语义保持不变。
- 回归发现旧诊断的 `completed` 缺少完整 RPC 过程约束；先保留三行伪完成的失败，再补充正常退出、提示 / 控制响应、稳定状态、收尾、应用确认及恢复门禁就绪约束。共享 `recovery_child` 在同一份字节上检查子身份和终态，避免状态命令只相信结果文件。运行器异常只核对启动前缀，不宣称进程树或实际影响已经结束。
- R5 的同步查询仅在真实 Pi 等待固定服务首个回复时读取文件，查询自身不推进 RPC、不启动程序；为其设置 10 秒测试上限。两组实测运行中均为未知，结束为完成 / 再次关闭。该检查与 D016 中禁止同步等待实际运行的约束适用对象不同。

## D016：用相同工具步骤和可观察文件条件验证真实恢复（2026-10-05）

- 实验分 repaired / unchanged 两组，每组各创建独立工作目录、规则副本及 A / B 的独立 Pi 配置目录。A、B 共用该组工作目录、提示、规则和固定工具调用 ID；均用真实 Pi 1.0.3、内置 read / write、自有准入扩展、无会话持久化。B 必须经过实际 `recovery start`，不能用普通 `run` 冒充恢复。
- 固定模型服务逐轮要求读取两个输入文件，再写 `effect.txt`。A 时两个输入均缺失；repaired 仅在 A 结束后由实验准备补齐文件，unchanged 保持缺失。B 的服务从零条工具历史开始，同样的调用 ID 重新出现，验证新会话、适配去重、规则与门禁没有继承 A 的状态。不添加人为延迟。
- 因为模型服务与实验脚本同进程，实际 A / B 及预期拒绝的启动尝试均异步启动并等待输出，避免同步阻塞回环服务；即使拒绝逻辑出现回归，也不能让测试自己阻塞服务。同步命令仅用于已完成日志的诊断、准备和确认，设置有界超时；实际进程转发与异常清理沿用已有实验 helper。
- repaired 组另验证确认后配置变化：旧计划拒绝且不占位、不启动、不新增请求；保留旧证据，再在新位置重新准备和明确确认实际使用的配置。两组完成后均重复启动并验证记录、工作区与请求数不变。实验以测试输入模拟确认，不认证真人身份。
- 摘要独立用 Node crypto 检查父、规则、配置、计划、确认、启动与结果的关联；日志、文件内容和请求历史分别核对。真实 Pi / 工具不等于真实模型：固定回复只证明接入和控制机制；人工修正输入不代表系统已经自动诊断或修复根因。环境 / 程序内容未绑定等 D015 边界继续适用。

## D015：启动另行原子占位，结果与确认分别保存（2026-10-05）

- 接口采用 `recovery start --plan <计划>`，取代早期拟议名称 `resume`；不追加新配置参数，实际执行已审阅的内容。启动前严格检查确认结构、所有摘要及当前来源，执行内存中的规则快照与配置，不在执行时重新加载规则文件。
- 固定输出为原计划路径追加 `.start.json`、`.run.jsonl`、`.result.json`。先以 `create_new` 与 `sync_all` 保存启动占位，再复核来源并调用既有启动器。占位一旦存在，包括半文件，均不再尝试创建进程；失败也需新准备和确认。已有子日志或结果阻止启动，不覆盖。
- 确认记录保持不可变，其中 `confirmed_not_started` 描述确认时刻。启动占位是消费凭据；没有结果时只能知道正在运行或结果未知，不能推测未启动、自动重试或承诺恰好一次。结果独立唯一写入，区分未创建进程、创建失败、启动后运行器异常与完整收尾，完整收尾仍需查看控制结果和返回码。
- 子进程使用明确工作目录、预留子 ID，创建全新规则引擎 / Pi 适配器 / 门禁；首条保持 `run_started` 及 PID，第二条 `run_linked` 绑定父运行、计划和确认摘要。诊断仅验证关联字段与本日志位置，不递归信任或执行外部文件。父日志不改。
- 文件复核不锁定文件系统，不认证人、不防御同权限整套篡改。程序二进制、脚本、环境和整个目录内容未绑定摘要；进程创建与关联日志之间仍有崩溃窗口。保留原有直接子进程清理和已准入工具不可撤销的边界，不新增系统工具或依赖。

## D014：计划绑定内容与原位置，确认只保存一次待启动关联（2026-10-05）

- 接口：`recovery prepare --parent <日志> --config <新配置.json> --out <计划.json>`；`recovery confirm --plan <计划.json>`。R2 只准备 / 确认，不执行程序；`resume`、启动消费与真实子日志留待 R3。
- 新配置明确提供继续原因、提示、规则路径、工作目录、程序路径、参数和两个期限；配置中的相对路径以配置文件所在目录解析。程序必须是存在的文件，不通过 PATH 或额外 shell 猜测；固定 `pi-rpc + tool-gate + block`，规则必须有效且非空。不记录环境变量，密钥继续由外部模型配置管理。
- 内容绑定：父日志用同一次读取的字节做诊断及 SHA-256；计划保存父运行 / 触发 / 关闭证据、配置和规则摘要、规范化新配置及规则快照、恢复 ID、预留子运行 ID、计划的规范路径。恢复 ID 派生自位置、准备时间及输入快照并在确认时重算，避免单改副本路径后仍复用旧 ID。使用 RustCrypto `sha2` 0.10.9，作为 Cargo 项目依赖并锁定，不安装系统工具、不自制哈希算法。
- 确认：完整展示后，必须输入 `CONFIRM <恢复 ID>` 并换行；取消、错误文本或 EOF 返回 3。读到确认后重新检查计划原字节、父日志、新配置和规则，变化返回 2。确认文件以 `create_new` 唯一创建并 `sync_all`，保存 `confirmed_not_started`、相关摘要和时间，返回 0；文件已存在（包括不完整占位）则拒绝覆盖。
- 原位置：计划不能复制 / 改名后再次确认；确认文件固定为原计划路径追加 `.confirmed.json`。相对路径或符号链接指向原计划时共享同一位置。一个父运行可有多份明确重新准备的计划；这里约束同一计划，不是永久禁止继续工作。
- 边界：SHA-256 检查变化，不认证人或抵御同权限者整套改写。确认输入可以由测试管道模拟，不宣称人类身份认证。确认尚未被启动消费；R3 必须再次复核并原子占用启动记录，不能仅凭 confirmed 状态重复启动。写入失败 / 崩溃可留下不完整文件，保留并报错，不自动删除重试；不宣称文件写入和进程启动具有事务原子性。
- 限额：父日志沿用 32 MiB，配置 / 规则各最多 1 MiB，计划最多 2 MiB；交互确认最多 1 KiB。准备不自动建输出目录、不覆盖任何已有文件。
- 依据：[RustCrypto sha2 API](https://docs.rs/sha2/0.10.9/sha2/)、[Rust create_new 契约](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.create_new)，以及现有 R1 证据检查与 R2–R4 设计。

## D013：只读诊断检查证据链，结论不作为启动许可（2026-10-05）

- 接口：`inspect --log <events.jsonl> [--format text|json]`。默认中文摘要，JSON 包含诊断状态、触发及引用、确认拒绝数、终态、继续条件和原因。日志只以数据读取，程序名和原始模型文本不执行、不直接回显。
- 返回码：完整且结构 / 关联有效的诊断返回 0，包括有效但不满足继续条件的 record、abort 或失败收尾；无效、不支持、不完整、读取失败返回 2。调用方必须读取 `eligible_for_manual_restart`，不能把退出 0 当作继续许可。
- 检查：版本 1、同一运行、从 1 连续递增的序号、完整行、首尾记录、向前引用；工具归一化与原文一致；规则、关闭、准入决定、应用确认、拒绝结果和终态计数相互对应。普通继续条件还要求 Pi RPC 就绪、提示接受、安静收尾、所有决定已确认、子进程正常退出及完整采集 / 适配。
- 限额：单文件最多 32 MiB、单行最多 1 MiB、最多 100,000 条记录；超限明确拒绝，不截断后推测结论。只读取普通文件，检查打开文件的大小与修改时间，发现变化则拒绝；这不是锁定或防篡改快照。较早日志即使版本号为 1，缺少当前关键字段也明确拒绝，不做隐式迁移。
- 信任范围：检查日志内部一致性，不认证日志作者，不防御同权限者重新伪造整条证据链。旧日志缺少规则快照，不能重新计算完整规则条件，也不能从工具开始推断磁盘效果。继续前仍需明确新配置、复核父日志并确认；`resume` 尚未实现。

## D012：人工恢复先新建关联运行，使用单文件导读交接（2026-10-05，设计已选定、尚未实现）

- 用户选择：查看原因后明确确认，开启关联的新运行；没有选择让原会话暂停后原地继续。
- 依据：现有运行单次提示，收尾关闭 stdin，规则和扩展拒绝状态随进程释放。`run_started` 也没有保存完整工作目录、命令参数和规则快照，不能把旧日志当作自动重放配置。
- 设计：先只读诊断已结束的门禁运行，再展示用户明确提供的新提示 / 规则 / 工作目录 / 程序参数，确认后建立独立运行及父子关联。旧日志不改，新运行重新计数并继续使用门禁；根因未解决时可以再次触发。
- 约束：缺少完整终态、证据损坏或控制失败时不进入普通恢复路径；确认后内容变更、取消和重复消费不能直接启动。启动与关联记录之间的崩溃窗口标为不确定，不自动重试或声称恰好一次执行。
- 范围：首版建议覆盖正常结束的 `blocked` / `gate_closed`，先做只读 `inspect`，再做确认及新运行。原会话恢复、自动重放、跨运行去重、严格调度尚未实施。
- 交接：根目录 `tutorial.md` 汇总意图、现状、阶段演进、六课源码路线和恢复方案；README 与 AGENTS 链接它。保留分阶段原始记录和验证摘要，避免整合时丢掉失败历史或把未来设计混入当前能力。

## D011：用批次与嵌套实测明确准入范围，暂不自动串行化（2026-10-05）

- 证据：真实 Pi 1.0.3 的批次准备先批准三个工具，两次失败后，同批已批准写入仍产生文件；后续两次新写入被拒绝。通过 `ctx.executeTool()` 的两层嵌套调用同样经过钩子，拒绝后重试没有重新获准。
- 选择：本阶段保留“关闭后不再批准新请求”的契约，不将普通 `block` 描述为取消整个批次或正在运行的父工具。实际文件效果、准入确认、父子关联和进程结束分别核对。
- 验证：四组固定模型回复驱动真实 Pi / 内置工具，不增加睡眠；仅测试扩展负责两层调用与故意在拒绝后重试，不进行直接文件写入。原始父子关系保留在 `output`，验证摘要将它关联至准入序号。
- 取舍：没有在钩子中等待上一工具结束来强行串行化。Pi 会先等待本批准备完成再执行，这样的等待可能阻塞整个批次。未来如要减少提前放行，需要单独设计调度策略并覆盖嵌套 / 并发，人工恢复也应在这个契约上设计。
- 限制：本轮不覆盖嵌套内部并行、任意深度、任意插件直接访问文件或派生进程。仍按不同工具调用累计失败；父工具若也报告失败会作为独立调用计数，不是根因去重。
- 来源：[Pi 扩展契约](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)、本地 `pi-agent-core/dist/agent-loop.js` / `nested-tool-calls.js`，以及 [边界实验报告](verification/pi-boundaries.md)。

## D010：沿 RPC 管道执行准入决定，规则保留在 Rust（2026-10-05）

- 选择：自有 Pi 扩展在 `tool_call` 中使用 RPC 的确认请求 / 响应子协议等待 Rust；协议名称固定为 `inhibitor-tool-gate/v1`。Rust 只回应此自有协议，不自动批准其它扩展的交互请求，不要求用户路由到页面。
- 启动：`--tool-gate` 先查询 `get_commands`，确认扩展注册的版本标记，再发送业务提示。Pi 使用显式扩展路径；CLI 的 `--no-extensions` 仍允许显式路径，并关闭自动发现。
- 策略：`record` 放行并记录；`block` 在首次规则触发后锁住本次运行的准入，不自动恢复。新请求收到否定后返回 `block: true, terminate: true`；无宿主、超时或信号取消默认拒绝，扩展在本次运行锁住拒绝状态。
- 证据：Rust 记录决定，扩展通知它实际采用的结果；按工具调用 ID 和名称关联。拒绝决定与确认分开，不把已发送拒绝等同于已经阻止。拒绝生成的合成工具错误单独记录，不进入既有规则计数。
- 取舍：这使用 Pi 已有 Extension UI 协议作为机器准入通道；不是新的通用认证协议。信任已加载的本地扩展与 Pi 进程，不防御同权限恶意代码或扩展替换。
- 并发：Pi 可先为同批工具完成全部准备再执行。只保证规则触发后不批准新请求；已批准的工具可能随后才执行，不能凭此承诺“所有尚未开始的调用都被撤销”。嵌套 / 并发专项验证不在首轮验收内。
- 准入前错误：Pi 对不存在的工具或无效参数可能在调用钩子之前返回失败。当前缺少足以区别“前置校验失败”和“绕过准入执行失败”的结构化证据，因此所有没有匹配准入的结果均保守按协议失败收尾，不凭错误文本猜测。代价是这类模型错误会提前结束运行；后续应补充可靠的前置校验分类。
- 来源：[扩展契约](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)、[RPC Extension UI](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc-extension-ui.md)；顺序依据已安装 `pi-agent-core/dist/agent-loop.js`。

## D009：修复 Windows RPC 退出的运行时条件，保留失败证据（2026-10-05）

- 实测：Node 24.17.0 下真实 Pi 两次中止均返回成功响应和空闲状态，但关闭 stdin 后出现 `UV_HANDLE_CLOSING` 断言，子进程退出码 `-1073740791`；启动器返回 2，最终 `control_outcome: failed`。
- 依据：Node [24.20.0 发布记录](https://nodejs.org/en/blog/release/v24.20.0) 明确包含 [#61999](https://github.com/nodejs/node/pull/61999) 的 Windows libuv 退出修复；Pi 上游 [#9507](https://github.com/earendil-works/pi/issues/9507) 也报告相同 RPC 关闭症状。当前根因判断是基于症状和上游修复的推断，需升级后的对照验证支持。
- 选择：依照用户的环境管理要求，通过 Scoop 安装修复版本 Node 24.20.0；保留旧版本，不改 Pi 依赖代码、不加入任意等待来掩盖崩溃。实验与 CI 固定同一版本便于复现。
- 结果：Scoop 安装及哈希校验通过，24.17.0 仍保留，npm 全局前缀不变；更新后仅记录 / 中止对照全部通过。结果支持上述运行时判断，但没有声称独立完成 Node 原生栈根因证明。

## D008：显式启用 RPC 中止，按证据区分请求、空闲与退出（2026-10-05）

- 选择：扩展 `run --format pi-rpc --prompt <文本> --on-trigger record|abort`；默认仍仅记录。RPC 独占子进程 stdin，单次发送一个提示，其它模式继承 stdin。
- 控制顺序：首次规则触发关联证据后发送 `clear_queue`，成功后发送 `abort`，成功后 `get_state`；仅接受匹配命令 ID、命令名和成功标记的响应。需要空闲且没有排队任务，随后关闭 stdin 请求进程退出。
- 理由：Pi 文档说明 `abort` 不会自动清除排队消息；`agent_end` 也不能证明没有后续工作。自然完成使用 `agent_settled`，中止使用响应与空闲状态证据，最终保留真实退出码。
- 期限：RPC 默认总运行期限 30 秒，控制或关闭收尾期限 5 秒，可显式配置；使用单调时钟。向 stdin 写入由独立线程负责，使不读取 stdin 的子进程不能卡住控制期限检查。
- 结果：正常完成保留子进程退出码；确认中止且进程正常退出时启动器返回 3，区别于普通成功；采集 / 适配 / 控制异常返回 2，强制结束直接子进程只属于异常清理。
- 取舍：这是合作式事后中止，有事件传输和命令处理的竞态，不能保证第三次工具从未开始，更不能撤销已完成动作。真实测试用受控延迟隔离中止路径，同时记录窗口中出现的工具调用。
- 来源：[RPC 生命周期与关闭](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)、[abort 与 clear_queue](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc-commands.md#abort)。

## D006：自查先复现，再修复；OCR 结论保持待完成（2026-10-05）

- 工具状态：本机 OCR 可运行，但没有配置模型端点；实际调用报错。用户随后明确选择先完成本次自查，OCR 稍后运行。人工审查不标记为 OCR 审查通过。
- 已复现问题：损坏 UTF-8 经替换解码后可被 Pi 适配器接受，导致无效记录参与计数，且启动器仍返回成功。
- 选择：采集结果新增 `invalid_utf8` 标记；Pi stdout 必须来自有效 UTF-8，损坏行只留诊断、不计数，并使适配结果不完整。普通文本模式维持原来的替换解码行为。
- 清理边界：本地实验超时时只需读取第一条已完整写入的启动记录来识别 Pi；不应因后续半条日志解析失败而跳过清理。
- 取舍：保持修复范围在编码完整性和本地实验超时清理，不在本轮引入产品级进程树熔断。

## D007：使用 OCR 委托规则，并补齐实验日志写入错误处理（2026-10-05）

- 更正：缺少 API 只阻止 OCR 自行调用模型，不阻止 `delegate preview` / `delegate rule`。直接使用现有 CLI，由当前助手按其规则逐组审查，无需安装额外插件。
- 审查来源：OCR JavaScript 规则明确要求异步错误处理和资源释放；核对本地实验发现，文件写入流的错误监听直到子进程关闭后才安装，运行中的日志写入错误可能成为未处理异常。
- 选择：抽取实验输出等待逻辑，在开始转发前监听 stdout/stderr 文件流错误，同时等待进程与输出结束；失败或超时走统一清理并保留原始错误。
- 范围：只改实验运行器，不引入新的产品级熔断能力；仍不保证任意后代进程树的清理。
