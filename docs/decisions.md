# 决策记录

## D001：先验证信息与规则，再讨论智能判断（2026-10-05 补记）

- 来源：用户明确要求“判错先放一边”，先获取信息并触发简单规则。
- 选择：显式规则、可回溯的触发依据；动作先固定为记录。
- 理由：先验证采集和触发是否可靠，使模型判断质量与基础链路分开验证。
- 代价：本阶段不能宣称具备自动熔断或错误治理闭环。

## D002：Pi 作为首个适配对象，规则保持独立（2026-10-05）

- 选择：新增 Pi JSON 输出适配，将工具结束事件转换为统一 `tool_completed` 事件；规则依赖统一事件，不依赖 Pi 的文本排版。
- 理由：Pi 提供 JSONL 事件和后续可用的 RPC / 扩展接口，符合管道启动器思路。
- 选择过程：此前提出先接本机已有的 Codex；用户提出 Pi 后，核对其公开接口，改用 Pi 做首轮实验。治理规则保留在独立 Rust 工程，避免耦合到某个 Agent 的内部实现。
- 取舍：先接工具结束事件；未识别的 Pi 事件仍保留原始输出，不试图映射完整协议。
- 失败含义：仅接受工具事件的布尔型 `isError`；不从 stderr、结果正文或模型自述推测失败。它只表示工具报告失败，不代表业务判断。
- 来源：[JSON 事件](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/json.md)、[RPC](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)、[扩展](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)。

## D003：先做不需要模型账号的真实 Pi 本地验证（2026-10-05）

- 来源：用户选择模型稍后配置。
- 选择：安装真实 Pi CLI，在本机启动确定性模型测试服务，引导 Pi 的真实 `read` 工具访问实验目录里的文件。
- 理由：不需要模型密钥或付费请求；工具执行、错误生成、事件输出和 Rust 采集仍走真实链路，便于重复验证。
- 取舍：这只能验证接入链路，不能证明真实模型会遵循任务或其推理质量；真实模型联调明确保留为待办。
- 安装：沿用 Scoop Node.js；Pi 固定版本、项目内 npm 依赖及锁文件，不安装全局 Pi。

## D004：本阶段观察，不实施中止（2026-10-05）

- 选择：规则触发仍只写入日志。确认采集、计数及证据关联准确后，再单独验证 RPC 中止。
- 理由：完成事件是事后信息；异步收到事件再发中止指令，不能保证下一次工具调用尚未开始。
- 后续：若需要严格阻止执行，单独验证执行前钩子或代理；中止不能撤销已经完成的操作。

## D005：显式去重并暴露证据不完整（2026-10-05）

- 选择：每次进程运行按 `toolCallId` 去重，仅一次 `tool_execution_end` 参与计数；失败次数是累计次数。
- 理由：重复记录不能使规则提前触发，成功结果里的错误文字也不应改变工具报告的状态。
- 异常：JSON 无效、字段类型错误、同一 ID 的状态冲突、stdout 行截断都会记录 `adapter_error`。继续收集后续信息，但启动器最终返回 2，并明确 `adapter_complete: false`。
- 取舍：保留原有每行 64 KiB 上限，不为本次小规模验证引入大对象存储。后续需要针对大工具结果单独设计；去重状态当前随调用数增长。
- 兼容：已有文本规则和 `matched_lines` 输出保持不变，事件规则新增 `matched_events`；事件规则漏配适配器时在启动进程前报错。

## D006：自查先复现，再修复；OCR 结论保持待完成（2026-10-05）

- 工具状态：本机 OCR 可运行，但没有配置模型端点；实际调用报错。用户随后明确选择先完成本次自查，OCR 稍后运行。人工审查不标记为 OCR 审查通过。
- 已复现问题：损坏 UTF-8 经替换解码后可被 Pi 适配器接受，导致无效记录参与计数，且启动器仍返回成功。
- 选择：采集结果新增 `invalid_utf8` 标记；Pi stdout 必须来自有效 UTF-8，损坏行只留诊断、不计数，并使适配结果不完整。普通文本模式维持原来的替换解码行为。
- 清理边界：本地实验超时时只需读取第一条已完整写入的启动记录来识别 Pi；不应因后续半条日志解析失败而跳过清理。
- 取舍：保持修复范围在编码完整性和本地实验超时清理，不在本轮引入产品级进程树熔断。

## D007：使用 OCR 委托规则，并补齐实验日志写入错误处理（2026-10-05）

- 更正：缺少 API 只阻止 OCR 自行调用模型，不阻止 `delegate preview` / `delegate rule`。直接使用现有 CLI，由当前助手按其规则逐组审查，无需安装额外插件。
- 审查来源：OCR JavaScript 规则明确要求异步错误处理和资源释放；核对本地实验发现，文件写入流的错误监听直到子进程关闭后才安装，运行中的日志写入错误可能成为未处理异常。
- 选择：抽取实验输出等待逻辑，在开始转发前监听 stdout/stderr 文件流错误，同时等待进程与输出结束；失败或超时走统一清理并保留原始错误。
- 范围：只改实验运行器，不引入新的产品级熔断能力；仍不保证任意后代进程树的清理。
